Independent research project

grader-preflightTesting the graders that score AI agents, before anyone trains on them

Agents that handle customer requests, write code or run workflows are trained and ranked by automatic graders: code that decides whether a task was done. When a grader is wrong, training rewards the wrong behaviour and leaderboards rank agents wrongly. I built a tool that tests a grader with no AI model in the loop, and checked it three ways on τ²-bench, a widely used benchmark for customer-service agents: against the grading bugs its authors later fixed, inside a small reinforcement-learning experiment, and on published runs by frontier agents.

The problem

A grader is part of the environment, and it can be wrong

In τ²-bench an agent talks to a simulated customer and calls tools that read and change a bank's, airline's or shop's database. The grader replays the agent's tool calls and compares the final database with the one a known-correct run produces. In July 2026 the benchmark's authors, Sierra, fixed several banking grading bugs in release v1.0.1 and reported that rescoring moved leaderboard results by up to about nine points.

×

It can fail a correct run

Before v1.0.1, one harmless extra lookup was logged into the database the grader compares, so a careful agent lost the whole task.

✓

It can pass a wrong run

Comparing only the final database can't see the order of steps, or a change that leaves nothing behind.

↻

It teaches what it rewards

In reinforcement learning the grader is the reward. A flaw doesn't just change a score; it changes what the agent learns to do.

The method

Change a correct run slightly, and check the grader's answer

For each task the benchmark ships one correct run. The preflight makes small changes whose right verdict is known in advance, runs them through the real environment and the unchanged grader, and flags any verdict that comes out wrong. It needs no AI model and covers a whole domain in about three minutes.

Results

What each phase showed

Every phase was pre-registered (hypotheses, thresholds and seeds written down and committed before the data was run). One of the five pre-registered hypotheses held (H1); H2 to H5 did not, and are reported as not held.

Bugs published by Sierra

1 · It finds known grading bugs

On the grader before the fix, an extra lookup was wrongly failed on 43 of 62 comparable banking tasks and a respelled number on 25 of 33; on the fixed grader, on 0 and 0. Controls in the unchanged domains: 0 mismatches.

Found here

2 · A grader bug changes what is learned

Policies trained on the buggy grader learned to stop right after the task; on the fixed one they kept checking. 7 of 10 buggy-grader seeds converged against 10 of 10, so mean true success fell 21 points. This is exploratory: both pre-registered hypotheses for this phase failed.

Found here

3 · Real frontier-agent runs

On 4 public leaderboard files the old grader would wrongly fail 118 runs (counterfactual: they ran on the fixed version). Phase 1's flags cover 87 (74%), short of the pre-registered 90%, so H5 failed: all 31 misses are the same bug, on 6 tasks where none of phase 1's five sampled extra reads used the tool these agents read.

New finding

4 · A blind spot in the fixed grader

Interest-discrepancy reports are silently discarded, so the grader sees that the report tool was used, never what the reports say or how many were filed. It affects 5 banking tasks; 3 of 41 real full-score runs on them filed wrong numbers.

The new finding

A report with wrong numbers still scores full marks

In task 096 the customer's savings interest was underpaid. The agent should credit both accounts and file a discrepancy report for each, with the correct and the applied interest rate. The report tool answers "Submitted Successfully", but it writes to a database table that doesn't exist, and the helper that writes silently returns instead of failing. The report is lost. The grader only sees, through a call log, that the report tool was used: filing one of the two reports, or reports with wrong rates, still scores full marks.

$ .tau2/v1.0.1/venv/bin/python examples/report_blind_spot.py

Uses only the task's own correct run, no published data or model. Same result on the grader before and after v1.0.1. The tool and the missing table are unchanged in the newest release, v2.0.0 (by reading its source; not run).

Next

What I'd do next

  • Try every possible extra lookup per task instead of five sampled ones: the one change that would have explained all 118 misgraded runs.
  • Add a check that alters the arguments of writes that leave nothing behind; it would have found the report blind spot from the gold runs alone.
  • Report the blind spot to the benchmark's maintainers with the one-command reproduction.
Technical details

Method, data, results and limits

Architecture

AdapterRuns tool calls on a live τ²-bench environment and scores them with τ²-bench's own, unchanged grader. Frozen since phase 1.
RelationsSix changes to a gold run, each with a known right verdict (P1, P3, P5 should pass; F1, F3, F6 should fail).
Phase 1 suiteRuns every relation on every task and compares the two grader versions case by case.
Phase 2 learnerA small policy trained with REINFORCE on real tool calls, rewarded by one grader version.
Phase 3 auditReplays published agent runs, regrades them under both versions and checks them against the relations.

The two grader versions are τ²-bench at pre-v1.0.1 (commit b51a6d6) and v1.0.1 (fc0055d), each in its own pinned environment built from τ²-bench's lockfile. One process loads one version; results are joined afterwards. Design notes: DESIGN.md. Hypotheses, thresholds, seeds and the nine dated amendments: PREREGISTRATION.md.

Phase 2: does the bug change what is learned?

A linear softmax policy over candidate tool calls, trained with REINFORCE on 30 banking training tasks (10 more held out), 10 seeds per grader, 3,000 episodes each. Every call is a real τ²-bench call graded by the real grader; true success is judged separately by the fixed grader plus an order check. The gate (the policy learns at all) held at 0.997.

Phase 3: published frontier-agent runs

Six public leaderboard trajectory files, chosen by a rule fixed before download: four banking (GPT-5.5, Claude Opus 4.7, Qwen3.8-max, Claude Opus 5; 388 runs each) and two airline (400 runs). Each run is replayed in both pinned environments and regraded. All four banking files turned out to have been produced on v1.0.1 itself, so the old grader's verdicts are counterfactual: what it would have said about these runs. Our regrade on v1.0.1 equals the leaderboard's recorded reward on 350–352 of 352 graded runs per file.

Model-assisted annotation (not human-validated)

For mistakes no grader sees, 24 runs were drawn by a fixed rule and labelled blind (no score, group or id) by two independent language-model annotators, Claude Sonnet and DeepSeek V4-Pro, against a written codebook. The codebook was clarified once after the first pass (amendment 9, disclosed): agreement on whether a run has a violation went from κ 0.59 to κ 0.70 (22 of 24). Disagreements were adjudicated against the full conversation, the bank's policy and the task's gold actions: 2 of the 16 full-score runs hide a violation, both false statements to the customer, one of them the wrong report numbers above. Adjudication was also done by a Claude model, the same family as one annotator. The pre-registered rule for growing the sample to about 80 runs was met but not run, for budget. Small, stratified and not human-checked: no rate is claimed.

The report blind spot

  • submit_interest_discrepancy_report_7294 calls add_to_db("interest_discrepancy_reports", …); the banking database model defines no such table, and add_to_db returns False for an unknown table. The tool ignores that and returns success. It is the only tool in the domain that writes to an undefined table.
  • The grader compares database hashes, so the report's contents never reach it; the discoverable-tool call log records the tool name, which is why leaving the report out fails.
  • Scope: tasks 093, 094, 095, 096, 097 file reports in their gold runs. In the held-out runs, 3 of 41 full-score runs on them filed reports whose numbers differ from gold.
  • Filing only one of task 096's two reports, or one of task 097's four, also scores full marks: the call log records the tool name once. Phase 1 counted the repeated report calls in tasks 096 and 097 as "no-effect writes" but had no relation that varied their arguments. Not found in τ²-bench's issues or changelog (searched 11 Nov 2026); issue #753 documents the related call-log behaviour.

Limits and threats to validity

  • Phase 3's old-grader verdicts are counterfactual; no agent here faced the old grader. 22%–30% of old-code replays are incompatible.
  • Four high-scoring agents and one domain; results describe their runs, not agents in general. Only the 1.x leaderboard version is tested; v2.0.0 is examined by code reading only.
  • Offline replay uses a text-search retrieval in place of the runs' embedding search. Searches are reads, so grading is unaffected, but replayed search outputs differ.
  • Phase 2's policy is open-loop and its true-success check is ours; it shows how a reward flaw shapes learning, not how a language model would behave.
  • Annotation is model-assisted and small (24 runs); the codebook was revised after a first pass, and the adjudicator is from the same model family as one annotator. The blind-spot evidence does not depend on it.
  • Two amendments (8, 9) were written after results were seen; both are dated and say what changed. No hypothesis, threshold or sample was changed after its data was seen.

What this project adds: a model-free grader test checked against a benchmark's real before-and-after fixes, its effect on learned behaviour, its coverage measured on held-out frontier-agent runs, and a previously unreported blind spot.

Phase 2's full sweep (experiment.py --full) takes about 1.5 hours on 8 cores. Phase 3 on published data needs the leaderboard files, downloaded separately; they are not redistributed here because their licence is not stated (τ²-bench issue #612). Commands in the README.
